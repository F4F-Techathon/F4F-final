# 多智能体后端接入辩论台

辩论台现在由真实的多智能体后端驱动。后端源码在 `Backend/eat-what-backend`，改动说明见 `Backend/ADAPTATIONS.md`。

- **后端负责：** 谁说、说什么、引用哪条资料、声音，以及听懂顾客说的话。
- **手机页负责：** 把每一轮演出来。Jev 仍然决定表情、手势和听众反应。手机页播放后端的声音，并告诉后端哪些内容真正被听到了。
- **后端没连上时：** 辩论台照旧由导演台（5174 或 `/director/`）发台词。

## 运行

```bash
# 终端 1：多智能体后端（127.0.0.1:8771）
cd Backend/eat-what-backend && ./start_mac.sh
# 终端 2：界面（开发 5173；或者 npm start 在 3000）
cd Frontend && npm run dev
```

- **访问方式：** 手机页只连自己的来源 `ws(s)://<页面主机>/api/agents/realtime`，界面服务器把它转发到 `AGENT_BACKEND_URL`（默认 `http://127.0.0.1:8771`）的 `/api/realtime`。所以手机经局域网或 HTTPS 访问时，不需要能直接连到后端。
- **状态：** `/api/status` 的 `agents` 字段显示后端是否在线、用的模型和语音。`npm start` 启动时也会打印后端地址。

## 一场辩论怎么走

1. **连接与开场准备：** 进入辩论页、开场动画结束后，页面连上后端。
   - 收到后端的第一条 `state` 后，页面发送 `session.start`：
     - **餐厅：** 台上受邀店主的 shop_uuid。界面里的店铺 id 就是 shop_uuid，两边一致。
     - **偏好：** 已确认的需求，即预算上限、安静、不能吃辣、过敏与忌口，加上顾客的原话。
     - **店主：** 名字、性别、年龄，后端用这些来说话和挑音色。
     - **声音：** 浏览器允许出声时自动开启；顾客自己关过声音的，重连后不会再打开。
     - **历史：** 回到一场已经开始的辩论时，带上本场已经演完的台词，后端接着往下讲，不再重新开场（见下文「离开再回来」）。
   - 页面同时发送 `mic.start`，让后端提前加载语音识别。
2. **开始讨论：** 收到角色名单 `restaurants.updated` 后，页面发送 `control: resume`，讨论开始。主持人 Orb 同时在本机说一句开场串场词（见下文「主持人串场」），填补后端写第一句的约 7 s。续接的讨论不说开场词。
3. **上台：** 每一轮的 `speech.ready` 到达时，这一轮变成一句台词：
   - 台词 id 用 turnId，后端的 `replyTo` 因而能直接对上；
   - 话题写成「行为 · 维度」，例如「开怼 · 价格」；
   - 引用的资料登记为依据卡片，显示在字幕下方。
4. **排队与镜像：** 台词进入本机队列（`stage.enqueueLocal`），并镜像给中继（`stage.mirror`）。导演台因此能看到这句以及它的 Jev 决策；刷新页面时不会重演。
5. **声音：** 后端的声音（PCM 24 kHz）先缓存，等这句开演时再播放。
   - 字幕跟着播放进度出字；
   - 这句的长度由音频决定，听众反应的节拍按估计时长安排；
   - 播放中每 100 ms 回报一次实际播放位置。
6. **回执：** 这句演完、完整文本也已到达后，页面回 `playback: ended`。
   - 有声音的轮次要等全部样本真正播完才回 `ended`，否则后端会拒收。
   - 被顾客打断的回 `interrupted`，后端取消的回 `interrupted`，台上演不了的回 `failed`。
7. **持续讨论：** 后端在当前这句播放期间预备下一轮，收到回执后立刻送出，所以通常没有空档。

## 一句说完，再说下一句

除了顾客插话，台上任何时候只有一个声音。

- **排队：** 舞台一次只演一句。有声音的轮次要等后端的声音真正播完（输出时钟走完所有样本），再停留 1.6 s 让人读完，下一句才开始。浏览器朗读的台词（Orb 的串场、导演台的台词）也要等朗读结束。
- **修掉的两处叠音：**
  - 后端配音的台词播到一半时，顾客暂停后继续，或者关掉声音再打开，浏览器会把这句剩下的字再朗读一遍，和后端的声音叠在一起。现在带自己声音的台词（`PlayingLine.voiced`）不再交给浏览器朗读。
  - 两台手机同时开着时，一台手机镜像给导演台的台词（后端的回合、Orb 的串场）会被另一台当成导演台的台词再演一遍，两台各说各的。现在镜像的台词带 `mirror: true`，导演台照常显示，别的手机跳过。
- **测试：** `scripts/line-playback.test.mjs` 用真实的 `useLinePlayback` 和一个假的后端声音来测。去掉这处保护时，这项测试会失败。

## 关键信息高亮与来源

后端每句都引用了资料（`evidence`）。字幕里凡是引用资料里真有的关键信息，都会标出来，并注明来源。

- **标什么（`src/agents/stage/highlights.ts`）：**
  - **数字：** 人均、单价、套餐价、折扣、评分、时长。台词写的是中文数字（「人均二十三」「二十六块九」「九五折」），资料里是阿拉伯数字（「参考人均23元」），两边换算后数值和单位类别都对上才算。
  - **名字：** 引用的推荐菜、套餐、代金券的名字（「香辣鸡腿堡」），整名或至少 3 个字的片段。
  - **评价原话：** 和引用的评价共有的至少 4 个字（「一股霉味」「安静典雅」），常用虚词不算。
  - 每句最多标 4 处，互不重叠，数字优先；引用资料里找不到的数字和说法一律不标。
- **怎么显示：**
  - 说到的关键信息加金色记号笔底，后面一个小圆标是来源编号；
  - 字幕下方列出「编号 · 说的话 · 资料类型 · 大众点评」，下面的依据卡片也标上同样的编号；
  - 点记号或来源条，会滚到对应的依据卡片并闪一下；
  - 还没说到的部分保持灰色，跟着声音逐字点亮。顾客自己的话不标。

## 地方菜店主说方言

和 agent-studio 原来的做法一样：方言台词加原文释义。

- **谁说方言：** 生成店主时按菜系选的口音（`contract.language`，例如川菜→四川话，粤菜和潮汕牛肉火锅→粤语，湘菜→湖南话）随 `session.start` 的 `characters[id].language` 发给后端。普通话和外国口音普通话不发。
- **后端：** 台词先用普通话写好并通过检查，再改写成这位店主的方言配音；普通话原句作为 `gloss` 随 `speech.ready` 送来。具体见 `Backend/ADAPTATIONS.md`「地方菜店主说方言」。
- **前端：**
  - 字幕显示方言；开口后，下方淡入「粤语 · 释义」加普通话原句；
  - 关键信息高亮照常作用在方言字幕上，因为数字和菜名改写时都保留；
  - 历史里同时存方言和释义（`HistoryEntry.gloss`）。离开再回来续接时，发回后端的是普通话原句，也就是后端最初写的那句。
- **代价：** 每句方言多一次模型调用（约 1–3 s）。后端在上一句播放时预生成，所以通常听不出来；只有开场第一句和插话后的第一句，会多等这一下。

## 顾客插话

- **后端识别（默认）：** 后端的语音管线就绪后（状态条显示「本地识别」），按住说话时，麦克风以 16 kHz、20 ms 一帧发往后端。
  - 松开后再补 1.2 s 静音，后端的语音检测据此判定这句说完；之后由 Whisper（本机 Apple GPU）转写。
  - 后端一检测到开口，就打断台上的发言；转写结果以顾客的台词上台，后端随即作答。
- **浏览器识别：** 后端识别不可用时，改用浏览器的语音识别。识别出的文字先上台，再以 `user.text` 发给后端。
- **两种识别都一样：** 顾客的话上台后，Orb 接一句串场话，选手的回应随后上台。

## 主持人串场

后端每轮要调用两次模型：调度器先选人，餐厅再写台词。所以开场第一句约要 7 s，顾客插话后的第一句回应要 6–10 s。这段时间由主持人 Orb 在本机先说一句短话。

- **时机：**
  - 会话就绪、开始讨论时，即收到第一份 `restaurants.updated` 之后。续接的讨论不说开场词；顾客最后那句还没人回答时，改说一句插话串场；
  - 顾客的话上台之后，即 `userSaid`。后端自己识别出来的话也算，虽然这句不会再发回后端。会话还没就绪时不说，因为就绪时本来就会有一句开场串场。
- **台词：** 从预置句里轮换，开场和插话各一组，定义在 `useAgentBackend.ts` 的 `INTERLUDES`。例如「各位选手准备好了吗？开始抢客！」「收到！让几位选手接一下你这个问题。」
- **演法：** 说话人是 `host`，话题为「串场」。台词用 `stage.enqueueLocal` 排进本机队列，再用 `stage.mirror` 镜像给导演台，Jev 照常决定表情动作。
  - 它**不是后端的回合**，不会发给后端，后端也不会等它的回执。
  - 开着声音时，由浏览器朗读，和后端的推荐语一样。
- **让位：** 后端的回应（`speech.ready`，或推荐结果 `result`）到达时：
  - 串场话还在队列里、没开演：用 `stage.drop(id, '后端的回应先到了')` 撤掉，回应直接上台；
  - 已经在演：照常演完，回应排在它后面。
  - 只在队列里还找得到这句时才调用 `stage.drop`。对已离开队列的台词调用 `drop`，会让播放器把正在演的这句停掉。
- **其他：**
  - 同一时间最多只有一句串场话在等。顾客连续插话时，旧的那句还没开演就撤掉，换成新的。
  - 会话结束或断开时，还没开演的串场话一并撤回，因为不会再有回应。
- **实测（5173，后端用 gemini-3.8-flash 和系统语音，开着声音）：**
  - 开场：连上后 0.6 s，Orb 开口；后端的第一句 7.0 s 到达时，Orb 已经说完，第一句直接上台。
  - 插话：顾客那句演到 3.4 s，Orb 接着说到 9.3 s；后端的回应 6.5 s 就到了，在 Orb 后面等了约 2.8 s。另一次是回应 7.0 s 到达，9.2 s 上台。
  - 等待期间不再空着，代价是回应偶尔要晚 2–3 s 上台。原因是 Orb 这句由浏览器朗读要 3.5–4 s，读完还有 1.6 s 的阅读停留。

## 离开再回来

离开辩论页（例如去看店铺详情）或刷新页面，后端会话都会关闭，回来时页面另开一个新会话。新会话的 `session.start` 带上 `history`，选手接着之前的内容讲，不会重新开场、再自我介绍一遍。辩论页里打开店铺资料抽屉不算离开，会话不会断。

- **来源：** `dining.history` 里本场已经演完的台词。
  - 从选店页点场记板开始一场新辩论（`startDebate`）时，它会清空，所以里面只有这一场的内容；
  - 刷新后，它从本机存储恢复。
- **内容：** 由 `brief.ts` 的 `historyForBackend` 生成。
  - 台上店主的台词：`{turnId, restaurantId, text, evidenceIds}`。turnId 用台词 id，也就是后端原来的 turnId，新会话的 `replyTo` 仍能对上。方言台词发普通话原句（`gloss`）；
  - 顾客的话：`{turnId, role: 'user', text}`；
  - Orb 和来宾的台词是本机的，不发；已经离场的店的台词也不发；
  - 最多发最近 200 项，每句最多 600 字、12 条依据。
- **后端的处理：** 见 `Backend/ADAPTATIONS.md`「续接讨论」。
  - 说过话的店不再自我介绍；还没开口的店第一次发言时照常亮相；
  - 用过的依据不再当作新资料；
  - 最后一项若是顾客的话，选手先回答它。
- **串场：** 续接时 Orb 不说开场词。顾客最后那句还没人回答时，Orb 改说一句插话串场。
- **调试：** `window.__stage.agent.trail` 的 `resume` 一项记着带回了几句；后端会发 `trace: session.resumed`。
- **实测（5 家同台）：** 讲了 5 句、顾客插了一句后离开，去看店铺详情，再返回。
  - 第一次返回：带回 6 项。侯伯直接回答了顾客的问题，没有再自我介绍；之前没开口的龙叔第一次亮相。
  - 第二次返回：带回 9 项。Orb 没有再说开场词，谢叔、侯伯直接接着聊。
  - 整场 14 句，每家只自我介绍了一次。

## 页面上的状态

| 状态 | 显示 |
|---|---|
| 连接中、准备中 | 正在连接多智能体… / 选手们正在读资料、定人设… |
| 辩论中 | 多智能体辩论中 · 模型 · 语音 · 本地识别 |
| 已暂停（恢复的会话会以暂停开场） | 卡片显示「选手们已经准备好了：点右下角 ▶ 继续」 |
| 等顾客回应 | 选手们在想怎么接你的话… |
| 模型连续失败（已自动重试 3 次） | 选手们暂时连不上模型，提供「再试一次」 |
| 断开、连不上 | 多智能体已断开，或后端没连上，可以用导演台发台词；提供「重新连接」 |

## 声音与暂停

- **关声音：** 正在说的这句立刻静音，但会播放到结束。后端从下一轮起改为纯文字（`control: audio, deferred`），因此不会掐断任何一句。
- **开声音：** 同样从下一轮起生效。
- **暂停：** 声音和字幕一起停下，继续时接着演。后端等待回执的时间设为 600 s，暂停期间不会超时。

## 模型与备用

- 所有智能体都先用已有设置，即 `.env.local` 里的 `LLM_*`。这里所说的智能体包括后端的调度器和各家餐厅，以及界面的需求整理。
- 已有设置失效时（连不上、密钥被拒、模型不存在、服务出错、超时），自动改用 `.env` 里的 `LLM_FALLBACK_*`：DeepSeek V4.1 Flash，模型 `deepseek-pro`。
- 失效后 5 分钟内先用备用。
- 备用模型的接口地址 `LLM_FALLBACK_BASE_URL` 还要向密钥发放方确认后填写。
- **2026-10-18 下午实测：** 已有设置的密钥额度用完了。服务商返回 403「令牌额度不足」（`pre_consume_token_quota_failed`），只有很短的请求偶尔能过，辩论每轮都失败，状态条显示「暂时连不上模型」。这正是需要备用模型的情况，填上接口地址后会自动切过去。

## 文件

| 文件 | 作用 |
|---|---|
| `src/agents/backend/protocol.ts` | 后端协议：事件类型、命令、二进制帧编解码，不依赖其他模块 |
| `src/agents/backend/session.ts` | WebSocket 会话：命令排队、按 epoch 丢弃旧事件和旧音频、麦克风帧编号 |
| `src/agents/backend/player.ts` | 播放后端声音：按句开播，用输出时钟计算已播样本，支持静音和暂停 |
| `src/agents/backend/mic.ts`，`public/worklets/mic-capture.js` | 麦克风采集：16 kHz、20 ms 一帧 |
| `src/agents/backend/brief.ts` | 需求转偏好、店主转角色（含口音）、后端引用转依据卡片、后端一轮转一句台词（含方言释义）、已演台词转续接历史 |
| `src/agents/stage/highlights.ts` | 台词里的关键信息（数字、菜名、评价原话）对上引用资料，供字幕高亮和标来源 |
| `src/composables/useAgentBackend.ts` | 辩论页的接线：会话、回执、插话、声音、状态，以及主持人串场（`createInterludes`、`INTERLUDES`） |
| `server/agentBackend.ts` | WebSocket 转发（`/api/agents/realtime`）和后端状态 |

开发版页面可以用以下钩子做调试和测试：

- `window.__stage.agent.trail`：最近的后端事件和回执；
- `window.__stage.say(text)`：模拟按住说话后识别出的文字；
- `window.__stage.agent.debugSpeech(pcm)`：把录好的 16 kHz 音频送进后端识别。

## 测试

- `scripts/agents-backend.test.mjs`：二进制帧格式、需求和店主的映射、一轮转一句台词、已演台词转续接历史（哪些台词带回、条数上限、随 `session.start` 发出）、会话的 epoch 过滤与麦克风帧编号、WebSocket 转发（含后端不在时返回 502），以及状态。
- `scripts/agents-interlude.test.mjs`：主持人串场。用 vite `ssrLoadModule` 加载真实的舞台 store 和 `useAgentBackend`，配上假 WebSocket，验证以下几点：
  - 开场和插话时 Orb 排进一句；
  - 这句不发给后端；
  - 回应先到时撤掉没开演的串场话，已在演的不打断；
  - 连续插话只留一句；
  - 会话结束时撤回；
  - 续接的讨论：已演的台词随 `session.start` 发出，Orb 不说开场词；顾客的问题还没人回答时，Orb 说插话串场。
- `scripts/intake.test.mjs`：需求整理的备用模型切换。
- `scripts/highlights.test.mjs`：中文数字换算；只标有单位或前缀的数字；价格、菜名、评价原话各自对上来源；资料里没有的不标；字幕按声音进度切分。
