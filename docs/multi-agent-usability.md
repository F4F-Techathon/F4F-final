# 多智能体辩论台 · 可用性测试报告

2026-10-18。测试对象是接入真实多智能体后端后的辩论台：手机页（5173），后端 `Backend/eat-what-backend` 运行在 8771。

**测试方法**

- 采用脚本化的任务测试，加上启发式走查，**没有真人被试**。
- 「顾客」的操作通过两种方式模拟：
  - 页面上的真实按钮；
  - 开发钩子：`__stage.say` 模拟浏览器识别出的文字，`__stage.agent.debugSpeech` 把 macOS 合成的人声送进后端的真实识别管线。
- 结论用来定位问题和衡量时延，不能代替真人测试。

## 测试环境

| 项目 | 配置 |
|---|---|
| 机器 | Apple M1 Pro，16 GB，macOS；无 NVIDIA GPU |
| 浏览器 | 桌面应用内置的 Chromium 浏览器，手机视口 375×812 |
| 店铺 | 台上 5 家真实店铺：灶上春（龙叔）、巡面（小黎）、湘稻香（郑姐）、宴春藏·知竹（侯伯）、丁香小鲜（谢姐） |
| 模型 | 沿用已有设置：`gemini-3.8-flash`，经 api.gpt.ge；思考关闭 |
| 语音合成 | macOS 系统语音。CosyVoice 3 在本机比实时慢约 7 倍，见下方测量 |
| 语音识别 | Whisper large-v3-turbo，跑在 Apple GPU 上 |
| 表演决策 | Jev（TypeSafe） |

## 任务与结果

| # | 任务 | 结果 | 关键数据 |
|---|---|---|---|
| T1 | 进入辩论页，等第一句 | 通过 | 连上后 6.5–7.7 s 出第一句；Jev 决策 0.47–0.68 s |
| T2 | 持续辩论（有声音） | 通过 | 每句 8–12 s；两句之间多为 0 s，偶尔 2–5 s（后端在播放期间预备下一轮） |
| T3 | 持续辩论（纯文字） | 通过 | 每句演 3.2–3.4 s，句间约 3.5 s；12 轮脚本测试中，句间等待中位数 4.3 s，最长 7.9 s |
| T4 | 插话：浏览器识别路径 | 通过 | 正在说的一句当场停下；后端的第一句回应在顾客开口后 6.2–10.7 s 到达 |
| T5 | 插话：后端识别路径（语音） | 通过（修复后） | 5 s 的录音一次性送入（不含说话本身的时长）：后端在 17–60 ms 内检测到开口并打断台上发言；约 2 s 后得到转写；回应在顾客那句演完后约 3 s 到达。转写为「等等,我不吃辣,人均50以内,谁家最便宜?」，准确。按实时说话推算，从松开到出转写约 1.5–2 s（静音判定 0.55 s，加 Whisper 0.9–1.5 s） |
| T6 | 回应是否切题 | 通过 | 说出「不吃辣、五十以内」后，人均 23 和 25 元的两家立刻出来作答、对比，并互相挑「辣」的问题；问「环境安静」，由安静的店作答 |
| T7 | 暂停后继续 | 通过 | 字幕停在第 8 个字，5 s 内不动；继续后讲完，回执被后端接受，下一句随即开始 |
| T8 | 讲到一半关声音，再打开 | 通过（修复后） | 这句静音后讲完，后端照常继续；之后两句为纯文字；重新打开后，下一句恢复声音 |
| T9 | 后端重启、断线后重连 | 通过 | 状态条提示断开，提供「重新连接」；断开期间舞台仍能演导演台的台词 |
| T10 | 模型持续失败（故意配置一个不存在的模型） | 通过（修复后） | 自动重试 3 次，约 10 s 后进入「暂时连不上模型」，可「再试一次」 |
| T11 | 主模型失效，切到备用模型 | 通过（实测切换） | 主模型被拒（403）后由备用作答，总共 2.9 s；接下来 5 分钟直接用备用 |
| T12 | 离开辩论页 | 通过 | 会话关闭，后端连接数归零，没有残留台词 |
| T13 | 做出决定，进入结果页 | 通过 | 结果页正常 |
| T14 | 导演台旁观 | 通过 | 后端说的每句都出现在导演台，带 Jev 的决策（如「自信推销 92% · 摊手展示 · 上前一步」） |

## 内容质量（12 轮脚本测试）

脚本固定了 5 家店、店主名和需求（「和朋友聚餐，想吃点有特色的，最好别太吵」，人均 150 以内），并在第 6 轮后插入一句顾客提问。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 发言分布 | 谢姐 7，侯伯 5；**另外 3 家始终没开口** | 谢姐 5，侯伯 4，龙叔、小黎、郑姐各 1；**前 6 轮 5 家全部亮相** |
| 行为分布 | 自荐 2、开怼 4、回击 3、对比 1、回答 2 | 自荐 3、对比 3、回击 3、开怼 2、回答 1 |
| 每句字数 | 21–41 字，没有超过 55 字上限的 | 同左 |
| 引用资料 | 每句 1–3 条 | 每句 1–3 条 |
| 回应顾客提问 | 6.2 s，切题 | 6.5 s，切题 |

示例（修复后）：

> 龙叔（自荐·菜品）：来啦，叫我龙叔！灶上春现炒面馆人均二十三，猪肝肉丝拌川火候死死的，嫩滑挂汁够烟火气。
>
> 小黎（开怼·环境）：哈喽，我是巡面的小黎！龙叔那地下室一股霉味实在难闻，我店里看着干净利落，吃得才舒心。

## 发现的问题与处理

| 级别 | 问题 | 原因 | 处理 |
|---|---|---|---|
| 高 | 5 家同台只有 2 家发言 | 调度器读到的节奏信息里没有发言分布，「开怼→回击」在两家之间循环 | 调度器的节奏提示加入 `speakerCounts` / `notYetSpoken`（只作提示），已修 |
| 高 | 关声音后，讨论卡住不动 | 关声音会停掉浏览器朗读，页面和后端声音共用的「播放中」标记被一并清掉，这句提前结束。回执报的播放量少于已发送量，被后端拒收，后端一直等待 | 后端声音改用独立标记；`ended` 回执一律等音频真正播完再发，已修 |
| 高 | 关声音会把正在说的那句直接掐掉 | 后端把声音设置变更当作打断 | 后端增加 `deferred` 参数，从下一轮起生效；页面把当前这句静音，已修 |
| 高 | 恢复的会话以暂停开场，页面只显示「等待选手发言…」，看起来像卡住 | 暂停开场是原有设计，但没有任何提示 | 卡片改为「选手们已经准备好了：点右下角 ▶ 继续」，状态条显示「讨论暂停中」，已修 |
| 中 | 后端会话结束后，旧会话的台词留在队列里，出现重复开场 | 会话结束时没有撤回未演的台词 | 会话结束、断开时撤回本会话未演的台词，已修 |
| 中 | 语音识别出现全角括号和乱码，并把「不吃辣」听成「不吃啦」 | Whisper 会模仿提示词里的标点 | 本机识别改用纯词表提示，加入不吃辣、预算等常用词，已修 |
| 中 | 开着声音时，顾客自己说的话又被设备朗读一遍，白等约 5 s | 浏览器朗读覆盖了所有台词 | 顾客的台词不再朗读，已修 |
| 中 | 模型持续失败时显示「选手们说完了」，会误导顾客 | 没有区分「说完了」和「失败了」 | 新增失败状态：重试 3 次后显示「暂时连不上模型」，提供「再试一次」，已修 |
| 低 | 顾客插话后等待回应的几秒里，没有任何反馈 | — | 卡片显示「选手们在想怎么接你的话…」，已修 |

## 测量：本机替代 NVIDIA GPU 的方案

| 部件 | 方案 | 实测 |
|---|---|---|
| 语音合成：CosyVoice 3 | Apple GPU（MPS） | 实时率 6.9–7.2，首个音频块 15–20 s：不适合直播 |
| 语音合成：CosyVoice 3 | CPU | 实时率 7.1–8.7 |
| 语音合成：macOS 系统语音（直播默认） | CPU | 约 3 s 的句子渲染 0.8–1.6 s；每个音色首次使用要预热 |
| 语音识别：Whisper large-v3-turbo（默认） | Apple GPU | 5 s 语音 0.9–1.5 s，加载约 16 s |
| 语音识别：同一模型 | CPU | 约 3.3 s |

**模型首字延迟（同一服务商）**

| 模型 | 首字延迟 | 能否用于直播 |
|---|---|---|
| deepseek-v4-pro | 约 13.7 s | 太慢 |
| deepseek-v4-flash | 5.4–11.8 s | — |
| deepseek-v4.1-flash | 2.4–3.1 s | 可用，是真流式 |

## 遗留问题与建议

1. **插话后要等 6–10 s 才有回应。** 后端每轮要调用两次模型：先由调度器决定谁说，再由餐厅生成台词。
   - **已处理（前端）：** 顾客的话上台后，主持人 Orb 在本机接一句串场话，例如「收到！让几位选手接一下你这个问题。」，不发给后端。后端的回应到达时，串场话如果还没开演就撤掉；已经在演就照常演完。做法见 [multi-agent-backend.md](multi-agent-backend.md)「主持人串场」。
   - **实测：** 顾客那句演到 3.4 s，Orb 接着说到 9.3 s，回应 6.5 s 到达，等 Orb 说完后上台。等待期间不再空着，但开着声音时，回应会因此晚 2–3 s 上台：浏览器朗读 Orb 这句要 3.5–4 s，之后还有 1.6 s 的阅读停留。
   - **还可以做：**
     - 前端：串场话后面已有回应在排队时，缩短阅读停留；
     - 后端：先把第一个小分句送出来。
2. **开场要等约 7 s。**
   - **已处理（前端）：** 收到角色名单、讨论开始时，Orb 先说一句开场串场，例如「各位选手准备好了吗？开始抢客！」。
   - **实测：** 连上后 0.6 s 开口；后端的第一句 7.0 s 到达时，Orb 已经说完，第一句直接上台。
   - **续接的会话：** 离开再回来、刷新后恢复时，已经讲过的讨论不再说开场串场（见第 3 条）。只有顾客最后那句还没人回答时，Orb 才接一句插话串场。
3. **离开再回到辩论页会重新开场。** 原后端不支持续接旧会话（交接文档也写明了），回来后选手会重新开场、再自我介绍一次，之前的交锋全部丢失。
   - **已处理（后端 + 前端）：** 回到辩论页时，`session.start` 带上本场已经演完的台词 `history`：店主的台词，turnId 用台词 id；还有顾客的话。
     - 后端把这些回合写成已听历史：说过话的店不再自我介绍，用过的依据不再当作新资料；最后一句若是顾客的话，就先回答它。
     - 做法见 [multi-agent-backend.md](multi-agent-backend.md)「离开再回来」和 `Backend/ADAPTATIONS.md`「续接讨论」。
   - **实测：** 5 家同台，讲了 5 句、顾客插了一句后离开，去看店铺详情，再返回。
     - 第一次返回：带回 6 项。侯伯直接回答了顾客的问题，没有再自我介绍；之前没开口的龙叔第一次亮相。
     - 第二次返回：带回 9 项。Orb 没有再说开场词，谢叔、侯伯直接接着聊。
     - 整场 14 句，每家只自我介绍了一次。
   - **边界：** 被打断的那句，前端记的是整句，续接时也按整句算已听。原会话里每轮的行为（开怼、回击等）、维度和回应对象没有带回去，续接后第一轮的节奏检查只看得到台词本身。
4. **发言分布只是改善，还没有保证。** 顾客提问后，相关的两家会主导讨论。可以考虑对多久没发言的店再提高一点优先级。
5. **声音。** 系统语音能实时播放，但音色偏机械。CosyVoice 3 适合部署到有 CUDA 的机器上，或用来离线预合成固定台词（例如各家的开场白）。
6. **手机经局域网访问时，麦克风需要 HTTPS。** 做法见 HANDOVER.md 第 1 节。
7. **主模型额度已用完，备用模型还缺接口地址。** 需要填 DeepSeek（`deepseek-pro`）的 `LLM_FALLBACK_BASE_URL`；在此之前辩论台无法正常运行。填上后，补做 R1、R4 的有声直播实测。
8. **这次没覆盖到的：**
   - 真人被试、真实麦克风与环境噪声（语音路径用的是合成人声）；
   - Safari / iOS；
   - 超过 15 轮的长会话；
   - 多台手机同时连接。验证串场时顺带看到：两台手机同时连着中继时，一台手机镜像出去的本机台词（后端的回合、Orb 的串场话）会被另一台当作导演台的台词演出来；
   - 弱网。
