# Multi-Agent 前端交接：只约定形式

2026-10-18 · 当前后端已实现本机演示。

**业务内容的类型、字段名和字段类型由前端确定；传输方式、音频格式、回合绑定和打断流程由后端约定。前端提供现有数据结构，后端做适配。**

## 分工

- 前端：现有界面与角色展示、提供餐厅列表、控制麦克风采集、播放返回音频、回报播放进度。
- 后端：读取商户资料、构建人格与名字、Multi-Agent 调度、语音识别、TTS、偏好与会话管理。
- 业务数据：说话人、正文、回应对象、引用等如何组织，由前端给出结构；本交接不规定新的 TypeScript 类型或 SDK。

## 我们约定的形式

| 项目 | 约定 |
|---|---|
| 连接 | 同一条 WebSocket 双向通信，JSON 传信息，二进制传音频 |
| 文本 | 每轮一次完整的结构化结果，不逐 token 推文本 |
| 音频 | TTS 实时分块返回，前端按队列连续播放 |
| 绑定 | 用 sessionId、epoch、turnId、segmentId 关联会话、取消代次、发言和音频片段 |
| 打断 | 新 epoch 到达，立即停止旧声音、清空队列，丢弃旧代次的后续输出 |
| 播放回执 | 前端约每 100ms 报告实际播放位置，并报告播完/打断；后端据此更新已听历史 |
| 角色名单 | 餐厅列表更新、名字构建完成后，先返回全量角色名单，再发言 |

JSON 使用下面的通信外壳，业务内容放在 data；turnId 等关联信息需随对应内容返回。业务字段最终按前端结构适配。

```json
{"sessionId":"s1","seq":12,"epoch":2,"type":"text","data":{"turnId":"t1"}}
```

上面只展示外壳和关联字段，不是完整业务数据。谁在说话由后端明确返回，前端无需推断。

## 音频与播放的必要约定

- 麦克风上传：PCM s16le、单声道、16000Hz；每 20ms 一帧，即 320 样本、640 字节。开麦后持续上传，关麦后停止，不上传 WebM/Opus 文件块。
- TTS 下发：PCM s16le、单声道，目前 24000Hz，实际以音频开始消息为准；块长可变，没有 WAV 文件头。
- 二进制封包：`4 字节小端 JSON 头长度 + UTF-8 JSON 头 + PCM`。上传头携带 kind=mic、streamId、chunkSeq、sampleOffset；下发头携带 kind=tts、epoch、turnId、segmentId、speakerId、chunkSeq、sampleOffset。
- 回执包含 turnId、epoch、status、playedSamples。status 为 progress / ended / interrupted / failed；位置是本轮真正播到的样本数，不能用已接收或排队长度代替。
- 音频发送完不等于播放完。当前顺序是 audio.end → 完整 text → turn.generated；浏览器全部实际播完后才回 ended。漏回执会阻止下一轮交付。
- 打断时用旧回合、旧 epoch 回报最后实际位置，然后清队列；新 epoch 的回复正常接收。

## 接入流程

1. 连接 → 提交餐厅列表 → 收到角色名单 → 开始持续讨论。
2. 用户开麦 → 后端确认就绪 → 持续传 PCM；语音识别与指令处理在后端。
3. 收到音频就播放，收到完整文本就按前端结构展示；两者按回合 ID 关联。
4. 用户插话或更新名单 → 取消旧回复，按新会话状态继续。无新输入时也会持续讨论。
5. 断线后停止播放和采麦；当前重连建立新会话，尚不支持旧会话断线续传。

文字输入、暂停、重置和过程日志是已有调试能力，是否放进产品由前端决定。
