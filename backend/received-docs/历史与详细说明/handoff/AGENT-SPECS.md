# Multi-Agent 能力、设置与协作示例

> 本文六类角色方案已收敛为 [最终方案](./最终方案.md) 中的一个Coordinator与餐厅Agent，以下为早期能力讨论记录。

这是按 Frontend / F4F-battle 分工细化的设计提案，不是当前 Demo 已实现能力的清单。配套 [配置示例](./agent-config.example.json) 仅用于说明设置，不会被当前服务器自动加载。基础架构和仓库阅读依据见 [交接方案](./README.md)。

## 1. 首版采用六类逻辑角色

Preference、Candidate/Constraint、Coordinator、Restaurant × N、Evidence Verifier、Judge。Agent 是职责边界，不要求六个服务或六个不同模型。所有餐厅使用相同生成程序，每家加载自己的资料、人设和记忆。

| 角色 | 首版实现方式 | 是否公开发言 |
|---|---|---|
| Preference | 结构化模型解析 + 规则校验；明确命令走确定性处理 | 不发言，必要时产生澄清请求 |
| Candidate/Constraint | 确定性过滤、计算、排序 | 不发言 |
| Coordinator | 状态机 + 优先级调度；复杂意图可由模型辅助规划 | 不发言；控制说明只显示文字 |
| Restaurant × N | 同一个 LLM，多份角色上下文与会话记忆 | 发言主体 |
| Evidence Verifier | 结构化事实校验 + 必要的语义核验 | 不发言 |
| Judge | 确定性资格检查与排序；模型辅助解释取舍 | 输出推荐卡片，不自动成为主持人语音 |

共享记忆、事件发送、LiveKit/VAD/STT/TTS、Jev 和角色骨骼控制都是支撑模块，不必继续拆成独立会说话的 Agent。

## 2. 每个角色都应该配置什么

| 设置 | 用途 | 例子 |
|---|---|---|
| identity | 稳定身份与类型 | `restaurant:bashi`，与 rong 造型分离 |
| objective | 目标与成功条件 | 帮用户比较餐厅；餐厅可争取被选，但必须承认不匹配 |
| knowledge | 能读哪些资料、如何知道出处 | 本店数据、授权的对手事实、当前需求、相关历史 |
| permissions | 可以调用什么、是否能改状态 | 餐厅只能提议台词，不能自己移除对手或改预算 |
| input/output | 结构化字段、枚举、长度 | turn plan → 句子片段 + speechAct + evidenceIds |
| policy | 优先级、禁区、未知如何处理 | 硬条件不能被营销或评分覆盖；无证据不编造 |
| memory | 读取与写回的内容 | 已回应的问题、讲过的卖点、已播到哪句 |
| runtime | 模型引用、时限、取消、重试和降级 | 模型共享；最多一次修正；旧 epoch 不提交 |

不要只写一段人设提示词。目标、知识范围、状态权限与输出校验应落实到代码；提示词帮助表达，不能代替约束。

模型名称和密钥只在服务端配置。示例中的 `shared_chat_model` 是逻辑引用，不代表已选定或配置某个供应商。超时和长度数值是起始建议，需通过联调再调整。

## 3. Preference Agent：把自然语言变成可追踪的条件变更

**能力**：区分偏好和硬要求；识别查询、移除、换店、暂停、继续、推荐、选定；处理否定、改口、撤销和餐厅名称别名；给出低把握/多目标时的澄清项。不能仅凭关键词将所有出现的菜系加入“喜欢”。

**输入**：原话、输入来源、旧 profile、当前候选及别名、commandId、revision。

**设置**：字段表、hard/soft 规则、别名来源、歧义阈值、澄清策略、允许的 patch 操作。沿用 Frontend 的字段名，在核心内部将过敏等信息规范化为可多值的条件；适配旧页面时保持兼容。

**输出示例**（以下及后续例子均为设计示意，不是真实模型运行结果）：

用户：原来预算150，现在最多200；少辣就行，不用完全不辣。别踢走华叔。

```json
{
  "intent": "update_preferences",
  "patches": [
    {"op":"set","field":"maxBudget","value":200,"strength":"hard","sourceText":"现在最多200"},
    {"op":"set","field":"mild","value":true,"strength":"soft","sourceText":"少辣就行"},
    {"op":"set","field":"noSpice","value":false,"strength":"hard","sourceText":"不用完全不辣"}
  ],
  "rosterActions": [],
  "clarifications": []
}
```

`false` 表示撤销“必须完全不辣”的条件，不是新增“必须有辣味”。“别踢走”不得触发移除。解析器只提议 patch，由会话控制器校验并原子提交。

**不确定时**：用户说“踢走那家贵的”，若多家价格相同或未知，返回澄清请求，不自行猜一家。STT 临时文本只显示，不提交业务；最终转写按 commandId 去重。

## 4. Candidate / Constraint：决定谁有资格继续比较

**能力**：校验前端交来的店与资料；计算距离；按硬条件分为 eligible / excluded / unknown；在 eligible 内做软偏好排序。主动换店必须来自已提供的候选池或明确的数据检索适配器，不能生成一家不存在的店。

**设置**：硬条件列表、缺失值策略、坐标体系和距离口径、各项软偏好权重、候场补位策略、是否保留已拒绝记录。

价格、距离、辣度、过敏等字段按条件检查，资料未知不当作已满足。只有明确开启的硬条件才触发排除；“最好安静”资料未知不必剔除，但不能声称已满足。

**例子**：用户上限150元、不吃辣。使用 Frontend 的虚构演示资料：

| 店 | 判断 | 原因 |
|---|---|---|
| 巴适川菜 85元，spice=2 | excluded | 不满足完全不辣；“可以少辣”不等于已满足不辣 |
| 华记粤点 128元，spice=0 | eligible | 满足当前两项硬条件 |
| Chez Pierre 198元 | excluded | 超预算，氛围和评分不能抵消 |

如果用户只说“少辣”，则应设为软偏好；巴适可以继续比较，但不能把当前 spice=2 改写成0。资料未覆盖的过敏要求应进入 unknown/不可确认状态，不能由模型保证满足。

**权限**：可以生成资格判断与补位建议，不能擅自放宽用户预算或删掉限制。全部不合适时输出空 eligible 和具体原因。

## 5. Coordinator：无声导演，控制持续讨论

**能力**：管理阶段、名单、议程、当前回合、优先级与取消；点名谁优先答谁；被质疑者有回应机会；检查内容是否推进；等待播放/阅读完成再换人；无人输入时自主安排下一回合。

**设置**：

- 调度优先级：停止/打断 > 条件/名单变化 > 点名问题 > 回应质疑 > 未覆盖比较 > 新证据补充。
- 发言公平：多人时同一家通常不连续占两轮；用户连续追问同一家可以例外。只有一家时允许继续解释利弊。
- 议题表：预算、口味、距离、环境、场景、菜品、短板、未知事项；只启用资料支持的议题。
- 长度：通常1–2句、约40–90汉字；接 Battle 时每轮不超过300字。
- 预取：最多准备下一轮，不无限堆积播放队列。
- 重复策略：记录“谁已讲过什么”；同一卖点换一种措辞仍算重复，用户明确追问时可再次解释。
- 结束策略：暂停/选定/无候选时停；用户请求推荐才进入 Judge；信息耗尽时等待补充，不强行选店。

**输入**：用户事件、资格结果、会话记忆、最近发言、播放回执。

**输出是 TurnPlan，而不是主持人口播**：

```json
{
  "speakerRestaurantId":"huaji",
  "targetRestaurantId":"bashi",
  "replyToTurnIds":["t17"],
  "speechAct":"concede",
  "topic":"预算与口味取舍",
  "objective":"承认对方价格优势，再说明本店与清淡偏好的关系",
  "allowedFactRefs":["bashi.price","huaji.price","huaji.spice"],
  "maxChars":90,
  "revision":4,
  "epoch":2
}
```

此例假定预算200、清淡是软偏好，两家均可继续讨论。调度在上层执行，餐厅模型不能自己选择下一位发言者。

**打断**：检测开口即停媒体、推进 epoch；不用等 STT 完成才停。新最终文本到达后处理偏好/名单，再安排新回合。取消的文本与未播片段不能写成用户已经听过的事实。

## 6. Restaurant Agent：同一程序，多份角色设置

**能力**：围绕本轮目标进行推销、比较、质疑、回应、让步、澄清与承认短板。每轮先处理问题或回应对象，再补自己的卖点。它的目标是让用户理解取舍，不是无条件说服用户选自己。

**设置分四层**：

| 层 | 内容 | 修改位置 |
|---|---|---|
| 业务身份 | restaurantId、agentId | 核心 |
| 商户知识 | 价格、菜品、环境、限制、证据、日期、mock标记 | 数据层，不能放在人设里写死 |
| 对话人设 | 性格、句式、互动风格、承认短板方式 | 角色配置 |
| 表演绑定 | characterId、Battle catalog ID、语言/音色引用 | 表演适配层 |

三家可以这样区分（人设沿用 Battle 的方向，表格中的表达是建议）：

| 角色 | 性格与表达 | 被质疑时 | 不应出现 |
|---|---|---|---|
| 蓉姐 | 热情直接、短句、有生活气息 | 先接住质疑，再拿资料说话；不合适就承认 | 对不能吃辣的人继续劝“试一下就好” |
| 华叔 | 温和笃定、重具体比较、可轻微反问 | 承认价格差，再说明用户关心的维度 | 把慢条斯理写成长篇说教 |
| Pierre | 讲氛围和仪式感，表达有个性 | 承认溢价和价格限制 | 伪造优惠，或把预算问题嘲讽成用户不懂品味 |

核心先生成普通话语义台词，Battle 再处理方言、语气和具体动作，避免两边重复改写。Battle 人设文本中也夹带了“煲四小时”等商户说法，不能因为写在人设里就当成已经核验的事实。造型和性格可复用，商户事实以本次数据/证据为准。

**华叔输出例子**：

```json
{
  "speechAct":"concede",
  "emotion":"thinking",
  "segments":[
    {
      "text":"蓉姐这点我认，我家128元，确实比85元高。",
      "claims":["huaji.price=128","bashi.price=85"],
      "evidenceIds":["huaji-info","bashi-info"]
    },
    {
      "text":"不过你刚才偏向清淡，我这边资料标的是不辣，可以一起比较。",
      "claims":["huaji.spice=0"],
      "evidenceIds":["huaji-info"]
    }
  ]
}
```

这里暴露了一个真实的数据交接问题：Frontend 当前 `huaji-info` 文本并没有收录所有 Restaurant 字段。`spice=0` 虽然在结构化数据中存在，也需要数据适配器为它建立可查的来源记录；不能随手挂 `huaji-info` 就算核验成功。该例是预期的句子/事实结构，第二句在当前引用条件下应先补齐来源或被拒绝发布。

**权限和记忆**：只能读本店与本轮授权的对手资料；只能提交台词提议，不得改 profile、移除对手、宣布胜者或调用 TTS。维护本店讲过的事实、收到的质疑和已回答的问题。已移除实例停止生成。

## 7. Evidence Verifier：从“引用存在”升级为“引用支持说法”

**能力**：校验来源是否存在、是否属于被谈论的店、数值/单位/时间是否匹配、证据是否表达相反意思、评论是否被扩大成普遍事实。核验后才允许流出公开短句。

**设置**：必须引用的事实类型、可用来源表、数值容差/单位换算、缺失数据策略、最多修正次数、语义检查是否启用、降级方式。

**输入**：待发布短句、结构化 claims、evidenceIds、商户事实记录和原文。

**输出例子**：

```json
{
  "status":"reject",
  "segmentText":"评论说这里绝对安静，保证适合所有商务宴请。",
  "issues":[
    {"code":"overgeneralization","detail":"单条顾客体验不能支持绝对或所有场景保证"}
  ],
  "repairInstruction":"改成有顾客提到适合聊天，保留体验因时段而异的限制",
  "retryAllowed":true
}
```

三种结果：pass → 发布；repair → 限一次修正后重验；reject → 丢弃该句，换有证据的事实或标记未知。不让修正无限重试堵住实时链路。

**重要限制**：规则擅长检查ID、数值、枚举和原文引用；复杂语义核验可以用模型辅助，但不能把模型判断当成证明真实。真实资料、演示资料和主观评价必须保持标签。

实时性上，模型适配器可以流式接收 token，按短句边界形成待核验片段；核验通过后发 text.delta。整轮JSON完成后再切字不算真实增量输出。上面的JSON是逻辑输出形状，正式实现不能强制等待整个大对象才发布第一句。

## 8. Judge：给出有条件的推荐，不替用户决定

**能力**：只在用户请求推荐时，比较当前 eligible 集合，给出选择、理由、相对代价与未知事项。候选不足以支持推荐时允许返回空结果。

**设置**：触发条件、硬过滤规则、软权重、并列处理、理由数量、未知的表达方式、是否输出分数。首版建议只展示理由与证据，避免未经校准的“98分”制造精确感。

排序可用已知字段做可解释的规则；用户显式偏好权重最高。硬条件先判断，不与偏好混成一个可抵消的总分。模型负责简洁解释，不能推翻资格检查。

**例子**：上限150且完全不辣，资格结果只有华记粤点时，建议选华记，理由分别引用价格和辣度来源；同时说明资料中的限制。若用户随后明确移除华记，则 eligible 为空，不能改推荐超预算的 Pierre。

```json
{
  "restaurantId":null,
  "reasons":[],
  "caveats":["剩余候选无法同时满足当前预算和完全不辣要求"],
  "nextAction":"request_new_candidates_or_user_preference_change"
}
```

这是内部 Judge 提议。对外按现有接口提案发 `decision.proposed`，其中保留 restaurantId/reasons/caveats；内部 nextAction 转成界面提示，不能擅自修改条件。最终收到用户 selection.confirm 后才发 selection.confirmed。

## 9. 三个协作场景

### A. 用户只说完初始需求，之后不发命令

“两个人，预算200，想清淡一点。” → Preference 更新条件 → Constraint 核验候选 → Coordinator 选预算议题 → 蓉姐讲一个事实 → Verifier 通过后流出 → Battle 表演并回执 → Coordinator 让华叔回应价格/清淡取舍 → Pierre 说明套餐时段限制。主持人不插一段口播，不依赖每轮用户触发。

### B. 用户插话：别说价格了，我更在意安不安静

先取消当前回合 → Preference 将 quiet 设为软偏好并记录新的议题重点 → Coordinator 跳过重复价格话题 → 选择有环境资料的店回应 → 用原评/商户来源说明，不将评价当成保证。没有资料的店承认未知。播放完后继续比较，不自动宣布胜者。

### C. 用户插话：踢走华叔，然后帮我选

一句话包含两个动作：取消旧回合 → 解析当前“华叔”究竟绑定哪家业务餐厅 → 提交移除并更新 revision → 重算 eligible → Judge 在剩余集合内推荐。不能先按旧名单推荐再移除；没有候选时说明无法推荐。所有旧 epoch 的文本与音频迟到包都丢弃。

## 10. 怎样验证这些能力

| 角色 | 至少一个成功例 | 至少一个反例 |
|---|---|---|
| Preference | 150改200、撤销不辣 | “别踢走华叔”不能移除 |
| Constraint | 硬条件合格者保留 | 高评分不能抵消超预算；未知不自动变符合 |
| Coordinator | 点名回应、无指令续聊 | 不在历史/证据面板打开时继续堆积发言 |
| Restaurant | 回应前一位观点、承认短板 | 不重复介绍，不生成没有来源的优惠 |
| Verifier | 有来源的价格可以发布 | 有效ID但内容不支持时拒绝 |
| Judge | 仅在 eligible 内推荐 | 零候选不能硬选，推荐不等于用户确认 |

跨角色还需检查：同造型多店不串身份、打断后旧输出不复活、只播一个声音源、规则降级有标记、重连不重播历史音频。

首版先实现“状态/权限与校验 → 调度 → 角色表达 → 事件流”，再精修方言和表演细节。单轮多次大模型串行调用会拉长时延，因此明确指令、资格校验、状态变更与媒体取消优先用确定性逻辑完成。
