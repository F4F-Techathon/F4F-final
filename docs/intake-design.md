# Orb 需求对话设计

## 页面目标

把当前“语音结束后直接进入候场”改成“表达想法 → 整理需求 → 适量追问 → 用户确认”。用户决定聊到什么程度；模型不控制跳转，也不要求把所有信息填满。

沿用奶油底色、现有 Orb、统一字体和进入候场时 Orb 向上缩小的转场。页面主内容保持单列，适配手机和 iPad。

## 页面组成

初始沿用当前大 Orb 和一个“点击说话”按钮。

第一轮整理成功后，内容顺序为：

1. Orb：在页内轻轻上移、缩小，为需求卡留出空间。
2. 当前一句回应或追问：两行以内，每轮最多一个问题。
3. 一张持续更新的需求卡：以简短词组呈现已知需求。
4. 底部“继续说”语音按钮，按钮下方一行带下划线的小字“不方便？试试发文字”，以及较轻的“就这样，去挑饭店”入口。
   - 点小字后，语音按钮换成文字框和发送键，小字变为“想说话？改用语音”。回车发送，Shift+回车换行；用输入法选字时按的回车不会发送。
   - 打的字和语音的最终识别结果一样提交整理，追问、需求卡和确认都不变。
   - 浏览器不支持语音识别时，页面直接以文字框打开。

语音识别中的本次发言显示在 Orb 下方，最终识别结果再提交整理。保留上一轮需求卡，更新完成后只让变化的内容轻轻淡入。页面不累积聊天气泡，不展示 JSON、完整度百分比或分析过程。

需求卡按内容自然排布，不预先放置大量空格：

- 用餐：人数、场景、时间。
- 预算：人均范围。
- 位置：区域、距离。
- 口味：菜系、清淡或热闹等偏好。
- 忌口：明确不能吃的食材、过敏原及其他必须满足的限制。

没有提到的项先不展示。明确说“不限”的项可以展示“不限”。不能把系统默认的两人、静安寺或 19:30 当成用户已经表达的需求。

## 一次完整交互

用户：“和朋友吃饭，清淡一点，人均一百五以内。”

需求卡：

> 朋友聚餐 · 人均 ¥150 内 · 清淡一点

Orb：“大概想在哪一带吃？”

用户：“静安寺附近，走路别太远，三个人。”

需求卡更新：

> 3 人 · 朋友聚餐
>
> 人均 ¥150 内 · 静安寺附近
>
> 清淡一点 · 步行方便

“走路别太远”保留原意，不擅自变成具体公里数。位置坐标由地图服务解析。

用户可以继续说“预算改成两百”“其实是四个人”“菜系都可以”，也可以直接点“就这样，去挑饭店”。确认后才把当前需求交给选店，并播放原有 Orb 转场。

## 追问规则

- 每轮最多问一个问题，优先解决会明显影响选店的信息，例如区域、人均预算或模糊的硬性限制。
- 不重复问用户已经回答的问题。用户明确说“不限”“都可以”“先这样”后，相应项不再追问。
- 当已有信息足够时，可以回应“好，按这个方向去挑。”，不继续凑问题。
- 用户纠正时覆盖相应项；没有变化的需求保留。“不吃川菜”需要移除先前的川菜偏好，不能继续叠加。
- 区分偏好和必须满足的限制。“少辣”不等于“不吃辣”，“和朋友吃饭”不代表已知人数。
- 不把模型猜测、系统默认值或商家信息混入用户需求，不擅自推断精确地址、预算或忌口。
- 模型不返回用于自动跳转的“已完成”指令。是否进入下一阶段由用户操作决定。

## 语音与请求状态

| 状态 | Orb 与页面 | 操作 |
| --- | --- | --- |
| 初始 | 大 Orb 等待，显示“今晚想吃点什么？” | 点击说话 |
| 聆听 | 沿用聆听表情，显示本次识别内容 | 说好了 |
| 整理 | Orb 轻微抬眼思考，保留已有需求卡；显示“我整理一下…” | 等待这一轮结果，避免重复发送 |
| 可补充 | 更新需求卡，显示一句回应或追问 | 继续说 / 就这样，去挑饭店 |
| 请求失败 | 保留已有需求及本次发言，显示“这句没整理好，再试一次” | 重试这一轮；不把旧结果当成本次修改后的结果 |
| 确认 | 固定当前需求，结束语音、取消未完成请求 | 原有 Orb 转场进入候场 |

在整理中不能确认尚未处理的更改。离开页面时中止请求；过期响应不能覆盖后续对话。网络失败不自动编造模型结果。

## 模型输入与输出

前端只调用需求整理接口；API Key 由服务端代理使用。供应商 URL、模型名和请求协议在获得配置后确认，不提前假设接口兼容某种 SDK。

每次输入包含：当前对话消息、上一轮结构化需求、本次最终语音文本。模型输出一份完整的新需求快照和至多一个追问，避免前端猜测长文本里的信息。

输出约定：

```ts
interface IntakeResult {
  requirements: DiningRequirements
  reply: string
  question: string | null
}
```

`DiningRequirements` 的语义：

| 字段 | 表达方式 |
| --- | --- |
| 人数 | 正整数或未知 |
| 人均预算 | 上下限、明确不限或未知 |
| 位置 | 用户描述的地名或附近范围、明确不限或未知；不让模型生成坐标 |
| 距离 | 明确的距离限制，或“步行方便”等原始偏好 |
| 时间与场景 | 用户表达的内容，未提及则未知 |
| 菜系 | 指定菜系、排除菜系、明确不限或未知 |
| 偏好 | 清淡、安静、氛围等软性需求 |
| 必须满足的限制 | 不吃辣、忌口、过敏原等用户明确提出的要求 |

未知、明确不限、具体值需要区分。模型响应在进入页面状态前校验字段类型、合法数值、预算范围和文本长度；失败时保留上一份成功结果并允许重试。UI 文案由 `reply` 或 `question` 展示一句，避免两段重复说明。

## 与当前项目衔接

- `InputView.vue`：将语音 `onComplete` 的直接跳转改成提交本轮需求；新增确认入口、持续更新的需求卡和追问。
- 需求对话状态独立管理，保留当前轮次、草稿、已成功整理的结果和请求状态；返回补充时可以接着聊。开始新的饭局时清空。
- `useSpeechInput`：继续使用最终识别结果，取消和中间识别结果均不触发模型提交。
- Orb 增加整理状态；保留现有聆听、闲置和跨页移动。页内缩小时使用同一个 Orb，不能复制一个新 Orb 替换。
- 餐饮 store 只在用户确认时接收一次整理结果。不要每轮调用当前 `understand()`，它会重置选店和讨论状态。
- 通过明确的转换把确认结果交给现有筛选字段；位置交给地图服务解析，无法解析时请用户确认，不能使用模型生成的坐标。
- 现有 `Filters` 无法表达的排除菜系、多个过敏原等限制，接入时需要同时扩展筛选，不能只显示在卡片里却不执行。
- 对模型未给出的内容，界面与内部默认值分开处理；不新增用户未确认的硬性筛选。

已按此设计接入真实需求整理服务。请求状态、失败重试、用户确认与草稿恢复由 `src/stores/intake.ts` 和 `InputView.vue` 管理，服务端代理位于 `server/intake.ts`。浏览器语音识别和本地餐厅讨论仍保留各自的服务边界。
